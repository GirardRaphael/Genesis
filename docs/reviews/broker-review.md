## Reproduced blocking findings during integration

1. **P1 — certified matrix plan can create deadline-breaking ready trips.** An isolated fixture supplied a road matrix whose solution was certified, then a route response with 4,000 seconds per leg. The broker run finished `succeeded`, certificate `valid=True`, and persisted a ready trip whose drop-off ETAs were 8,000 and 16,000 seconds against 7,200-second deadlines. `materialize_broker_trips` uses fresh `_road_route` geometry/timings after certification without checking them against the frozen matrix or revalidating the executable schedule. Reject changed road evidence, or independently certify the exact persisted route and cost before committing it. Add a mismatch regression; never present the matrix certificate as a certificate of an unverified route.
2. **P1 — service time disappears from executable trips and fleet availability.** In an isolated fixture, both matrix and materialized road legs took 60 seconds, with 120 seconds of service at each of four stops. The certified plan's makespan was 720 seconds; the ready trip's simulation duration was 240 seconds and its stop ETAs were `[60, 120, 180, 240]`. The materialized dispatch clock omits service dwell, so it can mark deliveries complete and offer the van for another plan before the certified work ends. Preserve service dwell in stop completion/progress/availability, or explicitly separate arrival from service completion and keep the van unavailable until the latter. Test exact boundary values.
3. **P1 — live zero-fleet request reaches model dispatch.** With a local run store, all vans mocked unavailable and `ModelAdapter` replaced by a raising stub, `BrokerRuntime.execute()` reached `MODEL_DISPATCH_REACHED` in the planning role before the no-route diagnostic. No network call was made. A live request with no eligible van should emit a no-trip diagnostic before constructing an adapter or holding model funds; also guard the race in which vans become unavailable after API preflight.
4. **P2 — solution hash was optional.** `validate_solution(problem, solve_problem(problem, 0.2))` returned valid; removing `solution_hash` still returned valid. The output certificate therefore accepted an artifact without the declared identity. Require a present matching hash. The lead reports this has been changed and a regression added; final rereview must verify it on the stable tree.
5. **P1 — cancellation after trip commit could strand a van; corrected, final regression pending.** A deterministic local fixture intercepted `put_artifact` for the final `accepted_plan` artifact and called `store.cancel(run_id)` immediately after `materialize_broker_trips` committed. Initially, the run finished `cancelled` while its broker trip remained `ready`. A first start guard blocked execution but a process-loss injection after terminal `finish` still left the ready trip reserving the van. The current `Store.finish` retires owned ready trips in the same transaction as terminal cancellation. Repeating that exact injection now produced a cancelled run, cancelled trip and available van. The owner is adding a persistent regression; final review must inspect it.
6. **P2 — balanced search weighted time differently from its published objective; corrected, final regression pending.** `_score` uses `fleet_cost_cents + ceil(makespan_seconds × 50 / 60)`, while the original OR-Tools span coefficient rounded `50/60` up to one cent per second before search. In a hand-checkable one-van/two-pair matrix, order `[1,2,3,4]` is feasible at 40 cents/160 seconds and declared score 174; order `[3,4,1,2]` is feasible at 95 cents/100 seconds and declared score 179. Original `solve_problem(..., 2)` returned the latter. The current search scales monetary arcs and fixed cost by 60 and gives span its exact per-minute coefficient; rerunning the same instance selected `[1,2,3,4]` with score 174. A persistent regression and final-tree review remain pending.
7. **P1 company-readiness limit — cancelled onboard cargo was forgotten; local safety block corrected.** In a one-delivery fixture, the first trip was cancelled after pickup service completed and before drop-off. Its projected stops showed the pickup completed and drop-off pending; originally `fleet_snapshot` marked the van available and a second broker run assigned it new work. The current tree derives unresolved cargo from completed pickup minus drop-off service on cancelled trips. Repeating the fixture now reports `available=False`, `unresolved_cargo_parcels=5`, and start is guarded. There is deliberately no unload/return/transfer recovery workflow; a real operator cannot safely clear this hold without that audited process. Keep the company gate open.

The implementation owners received these exact reproductions and corrected the local-scope defects. The solver independently recomputes pickup/drop-off coverage, same-vehicle precedence, capacity, deadline completion, cost and objective from the frozen input; its tests include hand-checkable candidate strategies and tampered totals. The cargo recovery finding remains a commercial release gate because a blocked van cannot be physically unloaded or transferred in this prototype.

## Product-claim boundary

`BrokerRuntime` computes fleet snapshot, matrix, candidate, certificate and admissibility in deterministic tools before each live model explanation. The model output is stored and handed to the next role as evidence/explanation; it does not choose assignments or override the solver. The feature may accurately claim automatic, bounded multi-van allocation with a five-role observable explanation workflow. It should not claim autonomous LLM route selection, globally optimal plans or physically executed deliveries. This is a description check as well as a test check.

The approval applies only to the fingerprint above. Any later material source or contract change requires an affected recheck and a new review. The [transport-company audit](transport-audit-review.md) and [release checklist](../TRANSPORT-CHECKLIST.md) retain the authentication, provider, GPS, cargo recovery, privacy and production resilience gates.
